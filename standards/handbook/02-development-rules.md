下面是 `standards/handbook/02-development-rules.md`。

这个文件的作用是**项目开发宪法级规则**。它不是代码风格（03负责），也不是流程（04负责），而是规定：任何开发者或 AI Agent 修改项目时，哪些原则不可违反。

# Development Rules

## 1. 文档定位

本文档定义得心实验室项目的开发约束。

所有开发者、AI Agent、自动化工具在修改代码、设计功能、引入依赖时，必须遵守本文档。

目标：

- 保持系统长期可维护；
- 保持架构稳定；
- 降低多人协作成本；
- 防止 AI Agent 随意修改项目方向。

---

# 2. 总体开发原则

## 2.1 服务于产品目标

所有技术决策必须服务于：

> 帮助学生更好地理解和学习数学

禁止：

- 为技术炫技引入复杂方案；
- 因个人偏好改变架构；
- 引入与产品目标无关的系统。

---

## 2.2 优先简单可靠

默认选择：

- 成熟方案；
- 简单实现；
- 清晰结构。

避免：

- 过早抽象；
- 过度工程化；
- 为未来未知需求设计复杂系统。

---

## 2.3 保持边界清晰

每个模块必须拥有明确职责。

禁止：

- 业务逻辑跨层传播；
- 一个模块同时承担多个职责；
- 组件承担非展示任务。

---

# 3. 架构约束

## 3.1 分层原则

项目主要分为：


Data
↓
Core
↓
Render
↓
Application


---

## Data

负责：

- 数据来源；
- 数据访问；
- 数据结构。

不负责：

- 页面逻辑；
- 内容渲染；
- 用户交互。

---

## Core

负责：

- 业务能力；
- 核心服务；
- 引擎逻辑。

例如：

- Content Engine；
- Markdown Engine。

---

## Render

负责：

- 内容展示；
- HTML 渲染；
- UI 组合。

禁止：

- 调用数据库；
- 执行业务判断；
- 修改内容结构。

---

# 4. 内容系统规则

## 4.1 内容结构稳定原则

核心结构：

```
Course
  |
  Topic
  |
  └── Lesson
```

URL 结构：`/courses/{topic}/{lesson}`

URL 优先表达稳定的知识结构，而不是内部数据库组织结构。

Chapter 作为教学组织概念继续存在，但不作为 URL 层级。

未经设计评审，不得改变。

---

## 4.2 内容与展示分离

课程内容不是页面代码。

禁止：

- 将课程内容硬编码在 Vue Component 中；
- 在页面组件中编写教学逻辑。

正确方向：


Content Data

↓

Content Engine

↓

Renderer

↓

UI


---

## 4.3 Markdown Engine 独立原则

Markdown Engine：

负责：

- Markdown 解析；
- AST 转换；
- HTML 输出。

不负责：

- 课程业务；
- 用户数据；
- 学习进度。

## 4.4 内容渲染边界

内容处理必须保持明确的数据流：

```
Content Data
↓
Content Service
↓
Markdown Engine
↓
UI Component
↓
Page
```

各层职责：

### Service 层

负责：

- 获取内容；
- 组合业务数据；
- 调用内容处理引擎（如 Markdown Engine）；
- 输出页面所需结构（含 `bodyHtml`、`introHtml` 等已渲染字段）。

### Markdown Engine

负责：

- Markdown 解析；
- AST 转换；
- HTML 输出；
- 内容格式转换。

不负责：

- 课程业务；
- 用户状态；
- 页面逻辑。

### Composable 层

负责：

- API 调用；
- 状态管理；
- Loading / Error / Cache。

禁止：

- Markdown 转 HTML；
- 内容结构转换；
- 业务规则判断。

### Page / Component 层

负责：

- 页面组合；
- UI 展示；
- 用户交互。

禁止：

- 数据库访问；
- 内容解析；
- 业务计算。

---

# 5. 前端开发规则

## 5.1 Vue Component 职责

组件应遵循：

展示组件：

负责：

- 接收 props；
- 展示数据；
- 用户交互。

业务组件：

负责：

- 页面级组合；
- 调用 service。

---

禁止：

在纯展示组件中：

- 请求 API；
- 操作数据库；
- 处理复杂业务。

---

## 5.2 HTML 语义化

页面结构优先使用标准 HTML。

推荐：


main
article
section
aside
header
footer
nav


避免：

- 无意义 div 嵌套；
- 使用 CSS 模拟语义结构。

---

## 5.3 Renderer 规则

Renderer 必须保持纯展示。

允许：

- v-html；
- slot；
- class 控制；
- 样式处理。

禁止：

- markdown 转换；
- 内容查询；
- 业务判断。

---

## 5.4 Layout / Page 结构规则

Layout 提供全局唯一 `<main>` 包裹 `<slot />`。

Page 不负责创建 `<main>`。

Page 根节点优先使用最符合内容语义的 HTML 元素：

- `<article>`：独立完整的内容（课程、文章、关于页）；
- `<section>`：主题性内容分组（主题详情、练习、领域页）；
- `<nav>`：导航浏览页（知识地图）；
- `<div>`：仅当无明确语义或需要布局控制时。

`<div>` 仅作为布局容器存在，不承担内容语义。

禁止：

- Page 内创建 `<main>`；
- 用 `<div>` + class 模拟语义标签；
- 根节点无条件使用 `<div>`。

---

# 6. 数据规则

## 6.1 数据来源统一

业务数据必须通过：Service访问。

禁止：

页面直接：

- 查询数据库；
- 调用底层 API。

---

## 6.2 数据模型稳定

数据库 Schema 修改必须：

- 记录原因；
- 更新相关文档；
- 考虑迁移方案。

---

# 7. 依赖管理规则

## 7.1 引入新依赖

新增依赖必须考虑：

- 是否解决真实问题；
- 是否已有方案；
- 长期维护成本。

禁止：

- 因为流行而引入；
- 重复功能依赖。

---

## 7.2 技术选型

优先：

官方方案 > 社区成熟方案 > 自定义方案

---

# 8. AI Agent 工作限制

AI Agent 修改代码前必须：

1. 阅读相关标准文档；
2. 理解当前架构；
3. 判断修改影响范围。

---

AI Agent 禁止：

## 自行改变架构

例如：

- 新建新的 Engine；
- 改变模块职责；
- 删除核心抽象。

---

## 自行替换技术栈

例如：

- 更换 ORM；
- 更换 UI 框架；
- 更换内容系统。

---

## 随意优化

禁止：

- 未经需求提出的大规模重构；
- 修改已有稳定模块。

---

# 9. 修改原则

任何修改遵循：

```

先理解
↓
小范围修改
↓
验证
↓
记录

```

---

大型修改必须：

- 创建设计说明；
- 明确迁移方案；
- 更新 Decision Records。

---

# 10. 代码质量要求

提交代码必须：

- 类型明确；
- 命名清晰；
- 无明显重复；
- 保持模块职责。

禁止：

- 临时代码进入主分支；
- 注释解释错误设计；
- 通过复杂代码掩盖问题。

---

## 10.1 未完成功能标识规则

未实现的功能不得表现为已经完成。

禁止用默认值伪装系统能力：

```ts
// ✗ 禁止：用空数组伪装已实现的逻辑
return []

// ✗ 禁止：用固定状态伪装已实现的状态系统
status: 'not_started'
```

正确方式——使用明确表示未完成的状态：

```ts
status: 'unsupported'
status: 'pending'
```

并添加 TODO 说明功能预期和等待条件：

```ts
/**
 * TODO: Progress Engine MVP
 * 当前仅提供接口，不计算真实学习状态。
 * 学习记录暂未启用，返回空数组作为占位。
 */
```

### 原则

- 系统状态必须真实反映系统能力；
- 不存在的能力不能通过默认值伪装存在；
- TODO 必须包含：功能名称、当前行为、等待条件。

---

# 11. 测试要求

核心模块必须保证：

- 基本功能测试；
- 类型检查；
- 构建通过。

尤其：

- Content Engine；
- Markdown Engine；
- 数据访问层。

---

# 12. 规则优先级

发生冲突时：

项目愿景
↓
架构规范
↓
开发规则
↓
代码风格
↓
个人习惯


个人偏好不能覆盖项目规则。
